# Frontend framework support

Project Atlas profiles each frontend package before scanning it. The profile is
based on workspace manifests, declared dependencies, framework configuration,
and router directories. Adapters then emit one normalized graph without treating
all files as reusable components.

`scan.coverage.complete` means that every file discovered by the supported
patterns was parsed without a reported parser error. It is not a claim that
every framework semantic, generated component, or runtime dependency was
understood. A repository with detected frontend dependencies and zero supported
source candidates is explicitly degraded with a diagnostic.

## Current support matrix

| Project shape | Observed support | Deliberate limits or degraded cases |
| --- | --- | --- |
| React without a meta-framework | `.jsx`, `.tsx`, and JSX-bearing `.js` under root or `src` component trees; named/default function, arrow, wrapper, and class components; local typed props/defaults, `children`, JSX composition, static class names, local imports, dynamic imports, custom `useX` dependencies, and associated tests | Lowercase factories, null/string-only renderers, imported or utility-heavy prop types, and components hidden behind arbitrary higher-order wrappers may be missed. Custom path aliases other than `@/`, runtime-only registrations, computed class names, and hook internals are not expanded. |
| Next.js Pages Router | Root and `src/pages`; `.js`, `.jsx`, and `.tsx` pages; dynamic/catch-all paths; `_app`, `_document`, and `_error` as special nodes; reusable components remain distinct | API routes and non-visual `.ts` convention files are not component nodes. Re-exports and custom aliases can reduce exact import resolution. |
| Next.js App Router | Root and `src/app`; pages, nested layouts, templates, loading/error/not-found/global-error/default files, route groups, parallel slots, and intercepting routes; root and nested route paths; `"use client"` versus server-default modules; async server components and `next/dynamic` bindings; hybrid packages retain both App and Pages routes | Route handlers, metadata/SEO files, middleware, server actions, and generated artifacts are not component nodes. A parallel/intercepting page is a special node, not a reusable component or canonical route. Runtime is module-level and does not attempt React Flight execution analysis. |
| Vue 2 SFC | Standalone `.vue` discovery; plain Options API and `Vue.extend`; runtime props, emits when declared, `model`, mixins, imported components, template composition, slot outlets and scoped-slot props, Vue Router routes, styles, and tests | Global `Vue.component` registrations, class/decorator components, external `script src`, render-function-only relationships, object-spread option resolution, and Pug templates are not fully modeled. Consumer-side scoped-slot bindings are not a separate graph entity. |
| Vue 3 Options API | Standalone `.vue`; plain objects and `defineComponent`; runtime props/emits, `setup()` composable calls, component imports, template/slot contracts, Vue Router routes, styles, and tests | Inject/provide flow, directives, stores, arbitrary setup return flow, and dynamically resolved components remain compact import or name evidence rather than expanded nodes. |
| Vue 3 Composition API and `script setup` | Dual normal/setup scripts; `defineProps`, `withDefaults`, `defineEmits`, `defineSlots`, `defineModel`, imported prop types, composable names, component imports, template composition, slot outlets, and scoped-slot props | Macro aliases, compiler transforms outside standard SFC macros, complex conditional/mapped type expansion, and consumer-side slot dataflow are not fully evaluated. Composables are dependencies on the component, not inventory components. |
| Nuxt 2 | Declared Nuxt profile/version range, root `pages`, `layouts`, and `components`, Nuxt component names, page routes, default layout, Vue 2 SFC APIs, and auto-import-style unique convention edges | Named layout selection, plugins, middleware, modules, store files, and server/API files are not visual component nodes. |
| Nuxt 3 and 4 | Declared Nuxt profile/version range, root or `app/` pages/components, layouts, `app.vue`/`error.vue`, `.client.vue`/`.server.vue`, Vue 3 SFC APIs, and Nuxt runtime component names | `definePageMeta` and named-layout dataflow, layers outside declared workspaces, server routes, islands generated by modules, and module-specific conventions are not expanded. | Astro | `.astro` components, pages, layouts, `Props` interfaces, static imports, component composition, slots, quoted classes, client directives, and `server:defer`; `.md`, `.mdx`, and `.html` pages are represented as static route nodes; installed React/Vue integrations are scanned by their adapters | Content collections, endpoints, actions, middleware, framework integrations not declared in the package, dynamic component expressions, `class:list` token evaluation, Markdown/MDX component internals, and arbitrary frontmatter type computation are not expanded. Client hydration and server deferral are distinct edges. |

## Classification and relationships

Every code node has a path-qualified ID and a kind: `component`, `route`,
`layout`, or `special`. Reuse search and similarity operate only on
`component`; route/layout/special nodes remain visible for impact and
composition. Multiple exports in one file retain distinct symbol identities,
and equal component names in different packages never collapse into a global
node.

Composition is resolved in this order:

1. a same-file symbol;
2. an exact local import binding and resolved source path;
3. a framework convention only when the name has one unambiguous target.

Edges retain `exact`, `framework-convention`, or `inferred` resolution plus
source provenance. Conventional layout and route-parent edges are restricted
to the same framework and routing package scope. Next nested layouts use route
prefixes; Nuxt's default layout is conventional; Astro layouts normally connect
through explicit imports. Vue Router routes come from static route objects.
Astro `client:*` creates a hydration edge, while `server:defer` creates a
separate deferral edge.

Props, events, models, slots, scoped-slot outlet props, rendered children,
static class tokens, test paths, imports, and compact logic dependencies are
stored on nodes. Atlas does not build a full TypeScript program or framework
runtime graph during orientation. This keeps indexing local and bounded, while
focused inspection can expand the exact node ID when a decision needs more
source.

## Acceptance fixtures

[`fixtures/framework-support/acceptance.json`](../fixtures/framework-support/acceptance.json)
is the executable matrix for the cross-framework runtime regression. It covers
49 discovered files across 11 workspaces:

- React standalone;
- Vue 2 Options API, Vue 3 Options API, and Vue 3 `script setup`;
- Nuxt 2 and Nuxt 3, plus the separate Nuxt 4 adapter fixture;
- Next Pages and App Routers, each at root and/or under `src/`;
- route groups, parallel and intercepting routes, dynamic imports, and
  server/client modules;
- Astro components, layouts, static pages, React/Vue islands, client hydration,
  and server deferral.

The regression requires every discovered file to be accounted for as parsed,
intentionally skipped, or failed; checks the expected
component/route/layout/special node sets; verifies public APIs and slot
contracts; asserts API route handlers and uppercase non-visual utilities do not
become component nodes; and checks exact edges do not jump to a same-named
component in another package.

## Code UI and agent context

Code shows one collapsed coverage strip with the detected package technologies,
declared version ranges, parsed/candidate/skipped file counts, error count, and
at most five diagnostics. Routes, layouts, runtime, and special roles appear as small
node facts. The UI does not infer a healthy inventory when coverage is
incomplete, and it does not add a framework dashboard.

Codex receives the same profile and compact coverage counts in orientation and
task context. Candidate payloads contain IDs, kind, role, runtime, route path,
public API summaries, a few relationships/tests, and bounded impact. Raw class
arrays, full source, and the entire inventory are excluded. Selected and ranked
IDs are returned as expansion handles so Codex can inspect only unresolved
evidence.

## Compatibility and performance

- Graph schema version 4 adds profiles, coverage, richer node roles, exact
  import evidence, and framework-aware edges. Existing code indexes are
  reconstructible and should be rescanned; canonical Project Memory and design
  indexes are unaffected.
- Catalog identity now includes the exported symbol as well as framework and
  path. A rescan replaces sightings for the current checkout rather than
  merging same-file exports.
- Single-package, single-framework repositories retain incremental scanning.
  Mixed-framework and multi-package profiles currently use a full scan to avoid
  unsafe partial coverage.
- Similarity remains bounded and excludes route/layout/special nodes. Adapter
  parsing is package-local and no source is injected into an LLM.
- The acceptance scan is a correctness fixture, not a production performance
  guarantee. Large monorepos should track candidate files, parse errors,
  wall-clock duration, peak memory, nodes per file, exact-edge rate, and
  ambiguous convention references.

## Next phases

The next useful increments are semantic completeness, not broader file globs:

1. add named Nuxt layout and `definePageMeta` relationships;
2. resolve `tsconfig`/workspace aliases without starting a whole-program type
   checker;
3. model CSS modules and variant declarations as bounded references;
4. add MDX/content-component parsing and Astro content collections behind
   explicit capabilities;
5. re-enable safe incremental scans per package after configuration and
   cross-package invalidation tests.

Each increment should add a minimal fixture, a false-positive assertion, parser
coverage metrics, exact-edge accuracy, and a context-size ceiling before it
changes the GUI or agent contract.
